# Firebase setup runbook (FEAT-010 / DEC-007)

The active `iosApp.xcodeproj` is generated by XcodeGen (`mobile/iosApp/project.yml`) and
uses SwiftPM for Firebase Core, Analytics, Crashlytics, and Firestore. `Podfile` and
`Podfile.lock` belong to the separate CocoaPods/KMP workspace lane and are not resolved
by the XcodeGen project build. The production integration is a native Swift Firebase
bridge in `AppDelegate.swift`. Do not upgrade unrelated dependencies.

## Supplying the real config (out of band, never committed)

1. The Firebase iOS app is configured for `BUNDLE_ID=posing.camera.app` in
   project `camerapose-a0877` (2026-09-24).
2. Copy the downloaded `GoogleService-Info.plist` to `mobile/iosApp/iosApp/GoogleService-Info.plist`.
   - This exact path is git-ignored; the real file must never be committed.
   - `GoogleService-Info.plist.example` in this directory is a template with
      fake values only.
3. The same Firebase plist is intentionally used for both `Dev` and `Prod`;
   this lane does not split Firebase configuration files. No Xcode project
   change is required after regenerating from `project.yml` because the
   `iosApp` sources directory is included; otherwise add the file to the target
   manually.

## Firestore Configuration (`config/app`)

Dynamic app configuration is fetched from Firestore document collection `config`,
document `app` (`config/app`), with public read access (no Firebase Auth sign-in required).

### Document Schema for `config/app`:

| Field Name | Type | Default Value | Description |
| --- | --- | --- | --- |
| `api_baseurl` | String | `https://pose-extract-server-production.up.railway.app` | Base URL for the AI Pose backend API. Must be valid HTTP/HTTPS URL without trailing spaces. |
| `account_enabled` | Boolean or String | `false` | Enables/disables account sign-in, saved poses, and sync surfaces. Accepted true values: `true`, `1`, `yes` (case-insensitive). |
| `extractPoseEnabled` | Boolean | `true` | Enables/disables pose extraction UI entry points (Add Pose button, job submission, form submit). Defaults to `true` when missing, invalid, or offline. |

*Note: Firestore security rules for `config/app` should allow public read access without requiring authentication.*

## Xcode environment selection

Run the `Dev` or `Prod` scheme generated from `project.yml`. The selected
scheme resolves `AIPoseEnvironment` and `AIPoseBuildConfiguration` through the
matching `Config/*-*.xcconfig` file. Firebase remains best-effort and is not
used as the environment descriptor.

## Startup behavior

- On launch, `AppDelegate.swift` reads the plist from the app bundle and
  validates its shape (required keys present, `API_KEY` looks like a real key).
  Missing, malformed, or placeholder-shaped configs are skipped: the app boots
  without Firebase.
- First paint is **never blocked by network or Firestore**: the root view is built
  immediately from the last successfully fetched payload cached in UserDefaults. Before
  the first successful fetch, compile-time defaults are used.
- When configured, a background task fetches `config/app` from Firestore within a
  bounded 5-second endpoint update window. Successful payloads are cached. Fetch error
  or offline failure keeps the current cached/default values; missing fields in a successful
  document use their field defaults. The root view is rebuilt only if an applied value changes.
- Add `extractPoseEnabled` as a Boolean field to the public-readable `config/app` document.
  Set it to `false` to hide pose extraction and Jobs entry points; missing or invalid values
  default to `true`. The other fields are `api_baseurl` (String) and `account_enabled` (Boolean
  or parseable Boolean string; defaults to `false`).
- Debug Simulator runs can override flags with launch arguments:
  - `-AIPoseAccountEnabled true|false`
  - `-AIPoseExtractPoseEnabled true|false`
  - `-AIPoseAPIBaseURL <url>`
  (Compiled out of Release builds).

## dSYM handling (Crashlytics)

- Crashlytics dSYM upload is a release build concern. Run the standard
  Crashlytics upload-symbols step from CI or a local release archive.
- Upload failure must be treated as a diagnostic failure, never an app-launch
  failure. No dSYM upload runs during local verification.

## Verification gates

```
xcodegen generate --spec mobile/iosApp/project.yml --project mobile/iosApp

```

Archiving, TestFlight upload, and release signing are handled by release runbooks.
