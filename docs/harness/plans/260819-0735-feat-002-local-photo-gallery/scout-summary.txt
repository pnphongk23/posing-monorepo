## Deletion contract (Cook target, Lead decision)

| Concern | File:line | Evidence |
| --- | --- | --- |
| `deletePhoto` removes SQL row only | `mobile/shared/src/commonMain/kotlin/com/aipose/data/PhotoRepository.kt:35-37` | `queries.deletePhoto(id)`; **no file delete, no storage dependency** |
| Dialog promises permanent deletion | `mobile/composeApp/src/commonMain/kotlin/com/aipose/ui/screens/gallery/PhotoDetailDialog.kt:165-175` | `"This photo will be permanently deleted."` + `onDelete(photo.id)` |

| Photo spec BR-PHOTO-003 | `docs/spec/data/entities/photo.md` | Delete completes only when metadata **and** owned file are removed; leftover file ⇒ no success claim |
| Photo spec BR-PHOTO-006 | `docs/spec/data/entities/photo.md` | Deleting PersonalPose does **not** delete Photo (`poseId` SET NULL) — opposite direction, no conflict with Lead cascade |

**Gap:** `PhotoRepository` has no storage injection and no access to `Pose` queries;
the cascade contract requires both (Cook change). `insertCapturedPhoto`
(`PhotoRepository.kt:14-24`) sets `poseId = null`; no code currently sets a
non-null `poseId`, so the cascade is a forward-looking contract (FEAT-004
extraction persistence). `getPhotosByPoseId` exists in `Photo.sq`, implying a
Pose may be referenced by multiple Photos — multi-reference cascade semantics
need a Maintainer confirmation (see design.md Risks).

## Search (IN scope — Maintainer closed)

| Concern | File:line | Evidence |
| --- | --- | --- |
| Prototype filter semantics | `docs/prototype/scripts/app.js:343-352` | `gallerySearchQuery` → `titleMatch = photo.title` **OR** `tagMatch = photo.tag`, case-insensitive (`toLowerCase`) |
| Search listener removed | `docs/prototype/scripts/app.js:384` | `// Search listener removed (plumbing moved to dedicated search screen)` — gallery.html has **no visible search input** |
| Fixture fields | `docs/prototype/scripts/fixtures.js:248` `GALLERY_FIXTURES` | `title` = "Pose Match 1..6"; `tag` = pose name ("DANCING", "STANDING", …) |
| Production: no search | `GalleryScreen.kt` / `GalleryViewModel.kt` (full read) | **No** `query`/`filter` state; `GalleryUiState` has no search field — true delta |
| Production fields | `Photo.sq` + `docs/spec/data/entities/photo.md` | `poseName` (snapshot, default `''`), `poseId` optional FK → `Pose.name` |

**Mapping (Lead decision, document not re-litigate):** `Photo.poseName` ≈ title;
tag derives from linked pose name (`Pose.name` via `poseId`) or stored metadata
(`Photo.poseName`). Nuance: prototype fixture `title` ("Pose Match N") is
distinct from `tag` (pose name); production `Photo` has a single name-like field
(`poseName`), so title and tag both resolve to pose-name text in practice — flag
for Maintainer in DEC-004 / design.md.

## Platform parity — MATERIAL FINDING

| Concern | Evidence |
| --- | --- |
| No Android target | `mobile/composeApp/build.gradle.kts:10-12` and `mobile/shared/build.gradle.kts:9-11` declare **only** `iosX64/iosArm64/iosSimulatorArm64` |
| No `androidMain` source sets | `find mobile -type d -name androidMain` → none |
| No Android actuals | `getPlatformPoseStorage()`, `DatabaseDriverFactory`, `saveImageToPhotos` have iOS actuals only |
| No AGP / Android plugin | `libs.versions.toml` has no Android plugin; no `AndroidManifest.xml` |

**Implication:** "Android parity" is **not** a single `SaveToPhotos.android.kt`
actual. It requires adding an Android KMP target + AGP + `androidMain` source
sets + Android actuals for `saveImageToPhotos`, `getPlatformPoseStorage`, and
`DatabaseDriverFactory`, plus an Android app host. This is a material
build-platform addition — surfaced to Maintainer (see design.md Risks and
verification ledger `E-ANDROID-TARGET`).

**Resolution (2026-08-19):** Maintainer directs **iOS-first** — Android parity is
**deferred** to a future FEAT-002 slice, planned only after an Android KMP target
exists. `E-ANDROID-TARGET` and `E-ANDROID` are **Excluded** from this Plan.

## Scout conclusion

Five true deltas in scope: (1) gallery **search** is absent in production,
(2) **deletion** removes only the SQL row, (3) **Save to Photos** is iOS-only with
no success confirmation, (4) **dense 3-col grid** parity, (5) **Android** build
target parity. FEAT-002 is **draft**, so the Plan is non-executable until Product
Authority approves it. Two material items require Maintainer confirmation before
Cook: the Android build-target scope and the title/tag field mapping.
