# PLAN_DRAFT — Camera Redesign & Published Pose Guide Picker

**Status:** Draft candidate for independent Planning Review; no `PLAN_FINAL.md` or `READY_FOR_WORK` yet.

**Goal.** Redesign SCR-001-01 CameraScreen for FEAT-001 and add a full-screen FEAT-008 picker for published pose guides. Preserve permission/capture truth, local photo persistence, lifecycle cancellation, camera settings snapshots, and the verified `PreparedPoseReference`-to-Camera handoff.

**Chosen approach.** Make the picker a camera-owned full-screen child surface, entered from HDR-003 and returned directly to Camera. Reuse `PosesLibraryCoordinator`/`CommunityPose` for published paging. Remove `PoseDetailViewModel` from the picker: retain the selected community item locally, reuse the existing shared `SignInPromptController`/`SignInPrompt` for `SignInIntent.TRY_POSE`, then use `PoseApiService.downloadImageBytes` and `PoseImageVerification` to produce the existing verified `PreparedPoseReference`. Camera updates its active reference and overlay, then uses existing settings-preserving snapshot persistence. This is the simplest viable architecture because it avoids a new app-level route/back-stack contract while preserving `CameraTab` and `LocalCameraDismiss` behavior.

**Auth boundary and alternatives.** `PoseDetailScreen.kt:421-470,521-545` couples detail-owned private `_signInIntent`, `pendingTrySuccess`, and resume logic to `tryPose`; the picker must not instantiate or copy that view model. The compatible existing preparation seams are `PoseApiService.kt:337-355`, configured with the shared session transport at `PoseServiceLocator.kt:26-40`/`SessionBoundary.kt:77-85`, and `PreparedPoseReference.kt:31-81` for structural verification/data-URI construction. They handle asset preparation, not a new account contract. Guests use the existing `TRY_POSE` prompt and retry the retained selection only after real auth; cancellation/failure stays recoverable. Keeping the detail route is rejected because it adds unowned navigation coupling; unauthenticated direct download is rejected because the current Try flow gates guests at `PoseDetailScreen.kt:430-437`.

**Coordinate and lifecycle decisions.** SCR-001-01 §5 rows 6–8 are the HDR group and row 8 `HDR-003` is the governing guide affordance (`scr-001-01-camera.md:146-155`): top header beside Tools. The old bottom-right users button (`CameraScreen.kt:377-383,592-620`) is not the acceptance coordinate; the bottom rail remains thumbnail/shutter/flip. The existing contract exposes `CameraController.stopPreview()` and `startPreview()` (`CameraContract.kt:39-54`), not `resume()`. Entering the picker stops preview; Back or verified selection starts it only for authorized foreground Camera. The Swift bridge maps these commands to session active state and `MCamera` mount/unmount (`CameraViewController.swift:64-73,359-393`). AV contention and thermal behavior lack repo evidence; Phase 3 assigns physical-device acceptance and General Lead owns the pre-READY decision.
